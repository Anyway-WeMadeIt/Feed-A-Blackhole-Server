# 부하 테스트

서버가 동시에 몇 명의 요청까지 버티는지, 어디가 먼저 한계에 닿는지 보기 위한 도구다. 시나리오는 [k6](https://k6.io)로 쓰고, 로컬에서는 Docker로 앱과 MySQL을 띄워 시험한다.

| 파일 | 역할 |
| --- | --- |
| [k6/blackhole.js](k6/blackhole.js) | 시나리오. 가상 사용자 한 명이 계정 하나를 맡고, 골든 캠페인(`src/test/resources/fixtures/golden-campaign.json`)의 검증 통과 로그를 순서대로 동기화한다 |
| [compose.yaml](compose.yaml) | 로컬 시험 환경. 운영과 같은 `Dockerfile`로 앱을 빌드하고, 자원 제한으로 운영의 크기에 가깝게 맞춘다 |
| [compose.jfr.yaml](compose.jfr.yaml) | 앱의 CPU 프로파일(JFR)을 남기는 덮어쓰기 설정. `docker compose -f compose.yaml -f compose.jfr.yaml up -d app` |
| [capacity.sh](capacity.sh) | 요청당 로그 1개로 요청률을 단계로 올려 p95 500ms 이하를 통과하는 최대 요청률을 찾는 스크립트(크레딧 있음 → 소진 순서, `SKIP_A=1`로 소진만) |
| [measure.sh](measure.sh) | 요청(로그)당 앱·DB CPU와 SQL 문장 수를 재는 스크립트. 코드·설정을 바꾸기 전후 비교용(`measure.sh before`, `measure.sh g1 "-XX:+UseG1GC"`) |

서버는 로그를 검증해서 처리하므로 지어낸 값으로는 실제 처리 경로(판 시작, 결산, 노드 구매)가 실행되지 않는다. 그래서 클라이언트가 실제로 판을 돌려 만든 골든 캠페인을 쓴다. 캠페인이 끝나면 `RESET`부터 다시 보내고, 판 id는 바퀴마다 바꿔서 중복을 피한다.

## 시나리오

`SCENARIO` 환경변수로 고른다.

| 값 | 무엇을 보나 | 주요 설정 |
| --- | --- | --- |
| `smoke` | 스크립트가 맞는지(1명, 3회). 시험 전에 항상 먼저 한다 | `THINK_SCALE=0.05`로 대기를 줄인다 |
| `realistic` | 실제 사용 흐름. 사용자마다 로그인 한 번 뒤 분당 `SYNC_PER_MIN`건 속도로 동기화(로그 1~3개) | `VUS`(동시 사용자), `SYNC_PER_MIN`(기본 20), `RAMP`, `HOLD` |
| `stress` | 초당 요청 수를 단계로 올려 한계를 찾는다. 오류가 5%를 넘으면 중단 | `RATES`(예: `5,10,20`), `STEP`, `VUS`(계정 수 상한) |
| `abuse` | 계정을 얻은 공격자가 유효한 로그를 큰 묶음으로 계속 보내는 경우. 고정 요청률 | `ABUSE_RATE`(초당 요청), `BATCH`(요청당 로그 수, 최대 500), `DURATION` |

`abuse`에 `BATCH=2`를 주면 정상 크기의 동기화를 **고정 요청률**로 보내는 시험이 된다. 요청률별 응답 시간을 깔끔하게 비교할 때 쓴다.

## 로컬에서 실행

```bash
cd loadtest
docker compose build app
docker compose up -d app          # MySQL과 앱이 뜨고 헬스체크가 UP이 될 때까지 기다린다
SCENARIO=smoke VUS=1 THINK_SCALE=0.05 docker compose run --rm k6
SCENARIO=realistic VUS=100 SYNC_PER_MIN=20 RAMP=30s HOLD=2m docker compose run --rm k6
SCENARIO=abuse BATCH=500 ABUSE_RATE=2 DURATION=60s VUS=100 docker compose run --rm k6
docker compose --profile k6 down -v   # 끝나면 컨테이너와 볼륨을 지운다
```

- **`APP_CPUS`, `DB_CPUS`는 `up`뿐 아니라 `run`을 포함한 모든 `docker compose` 명령에 같은 값으로 줘야 한다.** 값이 다르면 compose가 컨테이너를 기본값으로 다시 만들어 버려 시험이 무효가 된다(실제로 겪었다).
- `APP_CPUS=0.4 DB_CPUS=0.2`는 운영 인스턴스가 CPU 크레딧을 다 쓴 상태(기준 성능 `t3.small` 20%×2, `db.t4g.micro` 10%×2)를 흉내 낸다. 기본값은 둘 다 2(크레딧이 있는 상태).
- 앱이 막 시작한 직후에는 JIT 컴파일 때문에 느리다. 제한된 CPU로 재측정할 때는 20초쯤 예열한 뒤 시작한다.
- 시험하는 PC가 운영 인스턴스보다 빠르고 k6도 같은 PC에서 돈다. **절대 수치가 아니라 비교와 병목의 위치를 보는 용도**다.

## 병목 분석과 개선 (2026-10-21)

목표는 서버 기기를 키우지 않고 **앱 자체의 처리량을 올리는 것**이다. 추측하지 않고 세 가지로 측정했다.

1. **SQL 다이제스트**(`performance_schema.events_statements_summary_by_digest`): 요청 하나에 어떤 SQL이 몇 번 나가는지
2. **JFR 프로파일**(`compose.jfr.yaml`): 앱 CPU가 어느 코드에 쓰이는지
3. **요청당 CPU**(`measure.sh`): 컨테이너의 cgroup CPU 사용 시간 ÷ 요청 수. 요청률이 안정적이라 전후 비교가 믿을 만하다. 한 번에 포화시키는 시험(초당 250건)은 JVM 예열 중 과부하로 결과가 흔들려서 버렸다(이 문서의 첫 측정도 같은 이유로 한계를 과소평가했고, 아래 "예열을 충분히 한 비교와 한계"가 정정값이다)

### 찾은 병목과 조치

| # | 병목 | 조치 | 효과 |
| --- | --- | --- | --- |
| 1 | **트랜잭션마다 `SET autocommit`이 2번**, 모든 문장의 SQL 해석을 드라이버가 되풀이 | Hikari `auto-commit=false` + Hibernate `provider_disables_autocommit`, 드라이버 `cachePrepStmts`·`useLocalSessionState` (`application.properties`) | 정상 크기 요청의 SQL 11.6 → 8.3문장 |
| 2 | **RUN_START마다 쿼리 직전 자동 flush**: `DUPLICATE_RUN_ID` 검사 쿼리 앞에서 바뀐 엔티티를 훑고 `UPDATE player_progress`를 매번 내보냄(로그 50개 묶음에서 요청당 16번) | `existsByAccountIdAndRunId`에 flush 모드 COMMIT 힌트(`BattleRunRepository`). 이 요청 안에서 만든 판은 IDENTITY라 저장 즉시 INSERT되어 flush 없이도 조회에 보인다 | 큰 묶음의 UPDATE 감소 |
| 3 | **`sync_log` INSERT가 로그마다 1문장**: IDENTITY 키라 JPA 배치가 꺼짐. 로그 500개 요청이 INSERT 500번 | JDBC 배치 + `rewriteBatchedStatements`(다중 행 INSERT 하나로 합침). `SyncLogBatchWriter` | 로그 500개 묶음의 SQL 1,348 → 670문장 |
| 4 | **GC가 운영에서 G1이 될 가능성**: 운영 컨테이너는 메모리 제한이 없어 JVM이 호스트 약 2GiB를 보고 G1을 고른다. 시험은 1.5GiB 제한이라 Serial이었다 | `Dockerfile`에 `-XX:+UseSerialGC` 고정 | G1은 같은 부하에서 CPU +22~24%. 운영도 시험한 구성과 같아짐 |

운영 JVM이 실제로 어떤 GC를 쓰는지는 수정 전에는 확인하지 못했다. 서버에서 `docker exec blackhole java -XX:+PrintFlagsFinal -version | grep -E "UseG1GC|UseSerialGC "`로 볼 수 있고(새 이미지에서는 `UseSerialGC`가 `true`), 실행 중인 프로세스의 옵션은 `docker top blackhole`에도 나온다.

### 개선 전후: 요청 크기별 (같은 방법, 크레딧 있는 상태, 커밋 동기화 완화, 예열 약 100초)

| 요청 | 앱 CPU | DB CPU | SQL 문장 | p95 |
| --- | --- | --- | --- | --- |
| 로그 2개(정상 크기) | 11.5 → **6.6ms**(−43%) | 6.0 → 2.9ms | 11.6 → 8.3 | 34 → **8ms** |
| 로그 50개 | 43.2 → **22.2ms**(−49%) | 32.3 → 17.5ms | 139 → 72 | 103 → 43ms |
| 로그 500개 | 349 → **184ms**(−47%) | 292 → 153ms | 1,348 → 670 | 776 → 368ms |

- 같은 스크립트(`measure.sh`)로 다시 돌린 값은 앱 5.9 / 18.3 / 164ms로, 반복 사이에 10~15% 정도 흔들린다. 개선 폭(40% 이상)에 비해 작아서 결론은 같다.
- **정정**: 이 줄에 "처리량 약 1.8배"라고 썼으나 확인되지 않았다. 요청당 CPU는 줄었지만 한계 지점은 개선 전후 같았다(아래). 또 위 표의 감소 폭은 예열 약 4,000건 시점의 값이고, 요청당 로그 1개를 충분히 예열한 상태에서는 −16% 정도였다(아래).
- 정상 크기 요청에서는 요청 하나당 고정 비용이 대부분이다(로그당 약 0.3~0.4ms, 고정 약 6ms). 남은 문장 8.3개 중 대부분은 진행도 조회·갱신, 노드 조회, 커밋 같은 필수 문장이다.
- 전체 테스트 374개와 Checkstyle 통과. 테스트 두 곳(`NodePurchaseSyncTests`, `RunStartSyncTests`)은 `JdbcTemplate`으로 상태를 트랜잭션 없이 써서, auto-commit을 끈 뒤 커밋되지 않았다. 트랜잭션 안에서 쓰도록 고쳤다(운영 코드에는 트랜잭션 밖 쓰기가 없다).

### 예열을 충분히 한 비교와 한계 (2026-10-22)

`capacity.sh`로 쟀다. 요청당 로그 1개(상시 온라인 클라이언트)를 고정 요청률로 50초씩 단계를 올리며, **p95 500ms 이하·밀린 요청 0·오류 0**을 통과하는 최대 요청률을 찾는다. 크레딧 있음 구간을 먼저 재면서(수만 건 처리) JVM을 충분히 예열하고, 같은 프로세스에서 CPU 할당량을 줄여 크레딧 소진 구간을 쟀다.

**크레딧 있음(앱 2 CPU, DB 2 CPU): p95와 앱 코어 사용량**

| 요청률(건/초) | 개선 전 | 개선 후 |
| --- | --- | --- |
| 80 | 11ms / 0.30코어 | 7ms / 0.22코어 |
| 100 | 7ms / 0.32 | 8ms / 0.28 |
| 130 | 6ms / 0.34 | 7ms / 0.31 |
| 160 | 13ms / 0.53 | 11ms / 0.48 |
| 200 | 8ms / 0.51 | 9ms / 0.50 |
| 250 | 17ms / 0.77 | 8ms / 0.58 |
| 320 | 8ms / 0.79 | 5ms / 0.62 |
| **400** | **포화**: 처리 297건/초, p95 2.05초, 밀림 4,694, 앱 1.90코어 | **포화**: 처리 300건/초, p95 2.05초, 밀림 4,585, 앱 1.90코어 |

- 80~320 구간의 앱 코어 합계는 3.56 → 2.99(**−16%**)이고, 요청률마다 −2%~−27%로 고르지 않다. (20~60건/초는 시험 준비용 계정 생성 CPU 비중이 커서 비교에서 뺐다.)
- **한계(약 300건/초)는 개선 전후가 같았다.** 개선 후 코드로 포화 상태를 따로 살펴보니 앱이 CPU 상한(2코어)에 닿아 있었고(MySQL은 약 0.9코어, 행 잠금 대기 0, DB 연결 11개), 이때 요청당 CPU가 평소(약 2.5~3ms)의 약 2배(약 5.6ms)로 올랐다. 한계 근처에서는 문장 수를 줄인 효과보다 과부하 비효율이 크다.
- 사용자당 초당 0.097로그(골든 캠페인, 메뉴 시간 0)로 환산하면 약 300건/초는 **약 3,000명**, 분당 20건(초당 0.33)으로 잡으면 약 900명이다.

**크레딧 소진(앱 0.4 CPU, DB 0.2 CPU): 시험마다 다르게 나왔다**

| 실행 | 조건 | 개선 전 | 개선 후 |
| --- | --- | --- | --- |
| 1 | 크레딧 구간 뒤(요청 수만 건으로 예열) | 60건/초 통과(p95 54ms), 80건/초 탈락(503ms) | 80건/초 통과(p95 59ms), 상한 미확인 |
| 2 | 크레딧 구간의 과부하(400건/초) 직후 | 70건/초 탈락(1.2초) | 70건/초 탈락(1.5초) |
| 3 | 예열 요청 5,000건뿐 | 50건/초 탈락(1.2초) | 50건/초 탈락(2.6초) |

- 실행 2는 앞 단계의 과부하 상태가 이어져 오염된 값이다. 실행 3은 **JIT 컴파일이 요청 처리와 0.4코어를 다퉈** 응답이 밀린다.
- 따라서 소진 구간의 한계는 **예열 상태에 좌우되어 초당 50건 미만에서 80건 사이**이고, 개선 전후의 차이는 이 시험들로는 구분할 수 없다. 사용자 수로는 약 500~800명(초당 0.097로그 기준)이고, **배포 직후처럼 JVM이 막 시작한 상태에서는 더 낮을 수 있다.**

### 해보고 채택하지 않은 것

| 후보 | 이유 |
| --- | --- |
| `LogParser`의 `ObjectReader` 캐시 | 프로파일에서 로그 파싱 전체가 요청 CPU의 약 9%이고 그중 리더 생성은 일부라 효과가 작다 |
| JIT를 C1로 제한(`-XX:TieredStopAtLevel=1`) | 정상 크기 요청은 −22%였지만 로그 50개 묶음은 +74%로 크게 느려진다. 짧은 시험에서는 C2 컴파일 비용이 커 보여 오해하기 쉽다 |
| 응답·커밋·핸들러 최적화 | 프로파일에서 한 곳이 지배적이지 않고 각각 10% 안팎이다(핸들러 13%, 커밋 10%, 응답 직렬화 9%, 파싱 9%, `sync_log` 삽입 7%). 이득 대비 수정 위험이 크다 |

### 커밋 동기화(fsync)에 대하여

이 PC에서는 커밋 한 번에 4~6ms가 걸렸고(디스크 동기화), 개선 전에 요청당 `COMMIT`이 DB 시간의 대부분(평균 17ms)을 차지했다. 그래서 위 측정은 **커밋 동기화를 완화**(`innodb_flush_log_at_trx_commit=2`, `sync_binlog=0`)하고 앱 비용만 봤다. 운영 RDS는 동기화를 끄지 않으므로 요청 하나당 **커밋 1회의 지연**(EBS 쓰기 지연)이 응답 시간에 더해진다. 앱은 요청당 트랜잭션 하나, 커밋 약 1.1회로 이미 최소다.

## 해석

- **크레딧이 있는 동안은 정상 사용에 여유가 크다.** 동시 100명이 각자 분당 20건(초당 33건)을 쏴도 p95 38ms다. 한계는 **초당 약 300건**(앱 2코어 포화)이고, 예열을 충분히 한 상태의 측정이다(첫 측정의 "60~80건"은 과소평가).
- **크레딧 소진 상태의 한계는 초당 50건 미만~80건**으로 예열 상태에 따라 갈린다. 정상 사용(동시 100명, 초당 33건)은 그 안이지만, JVM이 막 시작한 배포 직후에는 여유가 크지 않을 수 있다.
- **100명이 분당 20건을 계속 보내는 최악의 경우는 크레딧 기준선 근처다.** 이때 앱 CPU 평균이 코어 하나의 36%이고, `t3.small`의 기준선은 합계 40%다. DB는 18%이고 `db.t4g.micro`의 기준선은 20%다. 이 PC의 코어가 운영 인스턴스보다 빨라서 실제로는 기준선을 넘어 크레딧이 서서히 줄 가능성이 높다. 평소 사용량은 이보다 훨씬 낮겠지만 "크레딧이 줄지 않는다"고 단정할 수 없다.
- **위험은 악의적 트래픽이다.** 인증 정보는 누구나 얻을 수 있고, 로그 검증을 통과하는 유효한 로그가 쓰이면 요청 수를 적게 유지하면서도 앱과 DB를 포화시키고 디스크를 채울 수 있다. **요청 빈도 제한만으로는 요청당 로그 수가 커서 부족하다.**
- 후속 방어 후보(미적용): ① 계정별 요청·로그 처리량 상한(앱 변경, 가장 효과적), ② `sync_log` 보존 기간 정리와 건너뛴·미처리 로그의 원문 미저장(런북 6장), ③ 전체 로그 처리량 안전망. IP별 제한은 정상 사용에는 영향이 없지만 공격에는 효과가 작고, **Nginx 본문 크기 상한은 쓰지 않는다**: 클라이언트 계약(5.6)에서 `413`은 `ProtocolError`(이번 실행을 오프라인으로 전환)라서 정상 사용자의 큰 백로그가 오프라인 처리된다.

## 운영 환경에서 하기 (`미검증`)

아직 하지 않았다. 할 때의 주의점:

- `BASE_URL`에 운영 도메인을 준다. 시나리오 준비 단계가 계정을 `VUS`개 만드는데, **Nginx 요청 제한(`02-rate-limit.conf`)이 걸려 있으면 준비가 실패하거나 `429`만 측정한다.** 시험 동안만 그 파일을 치우고 `reload`한 뒤, 끝나면 되돌린다([deploy/nginx/README.md](../deploy/nginx/README.md) "되돌리기").
- 작은 단계(`realistic`, 동시 20~50명)부터 올린다. 오류율이 5%를 넘으면 시나리오가 스스로 멈춘다.
- 지켜볼 것: CloudWatch의 EC2 CPU와 **CPU 크레딧 잔량**, RDS CPU·크레딧·연결 수·여유 메모리. 시험 중 CPU 알람 메일이 오는 것은 정상이다.
- 오래 돌릴 때(30~60분)는 크레딧이 줄어드는 속도를 본다. 짧은 시험은 버스트형 인스턴스의 한계를 보여 주지 못한다.
- 끝나면 시험 계정과 로그를 [런북](../docs/runbook.md) 6장의 절차로 지운다.
- `abuse` 시나리오를 운영 환경에 돌리면 실제로 서버가 포화하고 디스크가 찬다. 로컬 결과로 충분하면 운영에서는 하지 않는다.
