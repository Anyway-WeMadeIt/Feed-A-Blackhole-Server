# 작업 분배안 (4명)

- 상태: **분배 구상.** 작업 정의는 [offline-sync-work-breakdown.md](offline-sync-work-breakdown.md), 계약은 [api-spec.md](api-spec.md)에 있다. 이 문서는 그 작업들을 **누가 어떤 성격으로 맡을지**만 다루며 작업 정의를 바꾸지 않는다.
- 이름 대신 **역할**로 적었다: **S-A**(서버 설계), **S-B**(서버 구현), **C-A**(클라이언트 설계), **C-B**(클라이언트 구현). 실제 사람은 3장의 기준에 맞춰 넣는다.
- 규모는 작업 문서의 인일 추정이고, 일정은 10일 안의 목표 순서다.

## 1. 분배 원칙

1. **서버 2명, 클라이언트 2명**으로 영역을 나눈다. 각자 한 영역에 집중하고, 영역을 넘는 작업은 만들지 않는다.
2. **작업을 "설계형"과 "구현형"으로 나눈다.** 설계형은 작업 중 구조 결정이 필요할 수 있는 작업이고, 구현형은 **정답지**(명세, 기준 구현, fixture)가 있어서 그것에 맞추면 되는 작업이다.
3. **설계형은 구조 이해도가 높은 사람이 결정을 먼저 내리고, 구현자는 그 결정을 따른다.** 설계형 작업을 구현자가 맡더라도 막히지 않도록 착수 전에 **결정 목록**(4장)을 문서로 정해 둔다.
4. **먼저 구매 흐름(슬라이스 1)을 끝까지 붙이고, 그다음 전투(슬라이스 2)를 붙인다.** 동기화 구조의 위험을 일찍 드러내기 위해서다.

## 2. 작업의 성격

**설계형**은 작업 중 결정이 생길 수 있고 정답지가 없다. **구현형**은 정답지가 있고, 정답지를 만족하면 끝이다.

| 작업 | 영역 | 성격 | 결정이 들어가는 곳 / 정답지 |
|---|---|---|---|
| B2 서버 동기화 골격 | S | **설계형** | 핸들러 인터페이스, 트랜잭션과 락, 멱등 응답 보관, 형식 오류와 엔트리 거절의 경계. 다른 작업(B3, C3)이 이 구조 위에 선다 |
| C3 L1 검증 핸들러 | S | **설계형** | 검사 순서, 여유 계수와 보정 방식, 허용 오차, 거절 로그. 오탐과 미탐의 균형은 판단이 필요하다 |
| C1 `battle` 엔트리와 골든 케이스 | C | **설계형** | 킬 장부의 키와 기존 코드 확장 방식, 시작 스냅샷을 잡는 위치, 종료 사유, 헤드리스 시뮬레이션 정책 |
| C0 대응표와 기대값 fixture | C | **설계형** | 전투 코드를 읽고 정리해야 한다. 어떤 구성을 fixture로 뽑을지 선택이 필요하다 |
| B4 로그 기록기와 재적용기 | C | **설계형** | 파일 형식, 복구 규칙, 기존 `ProgressStore`와의 우선순위, 재적용 실패 처리 |
| B5 동기화 클라이언트 | C | **설계형** | 상태 기계, 서버 롤백을 저장소에 반영하는 방식, 트리거와 백오프, 사용자 안내 흐름 |
| A2 서버 전투 콘텐츠 로더 | S | 구현형 | 정답지: 검증 규칙 목록(작업 문서), 클라이언트 `ContentLoader` |
| B3 구매 검증기와 `reset` | S | 구현형 | 정답지: 클라이언트 `NodePurchase`의 구매 시퀀스 fixture, 검사 순서(작업 문서) |
| C2 스탯 표 계산기 | S | 구현형 | 정답지: C0 fixture |
| C4a 공급 계산 | S | 구현형 | 정답지: C0 fixture, 규칙(작업 문서) |
| C4b 허용 범위 계산 | S | 구현형 | 정답지: C0 fixture, `MassRule` 규칙(작업 문서) |
| F1 옛 API 제거와 문서 | S | 구현형 | 정답지: 시나리오 S7, 전체 테스트 통과 |
| A1 전투 콘텐츠 내보내기 | C | 구현형 | 정답지: 직렬화 규칙(작업 문서), 왕복 테스트 |
| A4' 클라이언트 번들 해시 | C | 구현형 | 정답지: 내보낸 파일 바이트의 해시와 같아야 한다 |
| A7' 노드 CSV 일치 확인 | C | 구현형 | 정답지: 양쪽 로더로 읽은 결과가 같다 |
| B5a-1 API 계층과 인증(전송, 인증 세션) | C | 구현형 | 정답지: api-spec의 토큰 흐름, 서버 `FakeClient`의 시나리오 |

## 3. 역할과 배정

| 역할 | 성격 | 작업 | 규모 | 어떤 사람이 맡나 |
|---|---|---|---|---|
| **S-A** 서버 설계 | 설계 중심 | **B2**, B3, **C3** | 10 | 명세와 검증 규칙을 가장 잘 아는 사람. 결정 목록을 쓰고 서버 쪽 결정을 맡는다 |
| **S-B** 서버 구현 | 구현 중심 | A2, C2, C4a, C4b, F1 | 9.5 | 정답지(fixture, 규칙 문서)를 보고 구현할 수 있는 사람. 서버 경험이 있으면 충분하다 |
| **C-A** 클라이언트 설계 | 설계 중심 | **C0**, **C1**, A1, A4', A7', B5a-2 | 8.5 | **전투 코드를 가장 잘 아는 사람.** 클라이언트 쪽 결정을 맡는다 |
| **C-B** 클라이언트 구현 | 구현 중심 | **B4**, **B5**, B5a-1 | 8.5 | 클라이언트 구조를 따라가며 구현할 수 있는 사람. B4, B5의 설계 결정은 4장의 결정 목록을 따른다 |

- **B3는 구현형이지만 S-A에게 둔다.** 핸들러 인터페이스를 만든 사람이 B2 직후에 가장 빨리 구현할 수 있고, 구매 흐름(슬라이스 1)을 일찍 붙이는 데 필요하다. S-B에게 여유가 생기면 넘긴다.
- **C-B는 설계형 작업(B4, B5)을 맡는다.** 대신 C-A가 B4의 결정 목록을, S-A가 B5의 결정 목록을 착수 전에 쓴다. 결정이 끝난 뒤의 B4, B5는 구현에 가깝다.
- **구현 중심 두 역할(S-B, C-B)에는 설계 결정이 열려 있지 않게** 하는 것이 목표다. 열린 결정이 생기면 6장의 질문 규칙을 따른다.

## 4. 설계형 작업의 결정 목록

착수 전에 해당 설계 담당이 **권장 기본값**을 확인하거나 바꿔서 확정한다. 확정한 내용은 해당 작업의 PR 본문에 한 줄씩 남긴다.

### B2 (S-A가 결정, S-A가 구현)

| 결정 | 권장 기본값 |
|---|---|
| 엔트리 핸들러 인터페이스 | `apply(작업 상태, 엔트리, 동기화 문맥) → 적용 \| 거절(코드)`. **거절할 때 작업 상태를 바꾸지 않는다.** 작업 상태는 가변 객체(Gold, 성장도, 순서 있는 노드 맵) |
| 같은 계정의 동시 요청 | 잠금을 즉시 시도하고 실패하면 `409 SYNC_IN_PROGRESS`(대기하지 않음) |

| 형식 오류의 경계 | 요청 구조 자체의 오류(잘못된 JSON, `batchId` 누락)는 `400`, 개별 엔트리의 형식 오류와 알 수 없는 `type`은 그 엔트리의 `MALFORMED_ENTRY` 거절 |
| `claimed` 비교 | Gold, 성장도, 노드 Rank(순서 무관). 불일치는 거절이 아니라 `claimMatched=false`와 서버 로그 |
| 한도 값 | 설정 파일로 뺀다(엔트리 50개, 본문 1 MB) |

## 7. 부하와 병목

| 역할 | 작업 | 설계 결정, 리뷰, 조율 | 합계 |
|---|---|---|---|
| S-A | 10 | 약 1.5 | **11.5** |
| S-B | 9.5 | 약 0.5 | 10 |
| C-A | 8.5 | 약 2 (결정 목록, 골든 케이스 지원, 통합) | 10.5 |
| C-B | 8.5 | 약 1.5 (사용자 안내, 통합) | 10 |

- **전체: 약 42인일 vs 4명 × 10일 = 40인일.** 약 5% 초과라 무리가 필요하다.
- **병목은 S-A**(B2 → B3 → C3, 합계 11.5)와 **S-B의 연쇄**(A2 → C2 → C4a, C4b)다. S-A의 C3는 S-B의 결과가 도착하는 순서(장부와 결산은 A2, 시작 스냅샷은 C2와 C4a, 공급 상한은 C4b)에 맞춰 안쪽부터 구현한다.
- **클라이언트 쪽은 의존 체인이 길다**(C-B의 B4 → B5a-1 → B5). 그래서 가짜 서버(B5a-2)를 C-A가 앞서 만들어 C-B가 서버 없이 시작하게 했다.

**일정이 밀릴 때 줄이는 순서** (앞에 있을수록 먼저 줄인다)

1. 조건부 작업 E, A7'(노드 CSV 일치 확인), F1의 문서 갱신 부분.
2. C3의 혜성 상한과 누적 시간 검사(둘 다 독립적인 개별 검사).
3. 골든 케이스의 판 수(수십 개 → 10여 개)와 실제 플레이 케이스.
4. B5의 사용자 안내 문구와 연출(확인 창 하나로 단순화).
5. **줄이지 않는 것:** 옛 API 제거, 장부와 결산 검증, 공급 상한, 서버 롤백의 저장소 반영, 로그의 즉시 저장.

**S-A의 부하를 덜려면:** B3(구현형)를 S-B나 Java에 익숙한 팀원에게 넘길 수 있다. 다만 C3의 입력 순서가 바뀌므로 S-B의 연쇄(C2, C4a, C4b)가 한 단계 늦어진다.

## 8. 사람에 맞춰 바꿀 때

| 상황 | 조정 |
|---|---|
| 명세 이해도가 가장 높은 사람이 서버가 아니라 클라이언트 쪽이다 | S-A와 C-A의 결정 목록을 서로 바꿔 쓴다(B5의 프로토콜 결정은 명세를 쓴 사람이 맡는다). 구현 배정은 영역을 유지한다 |
| 클라이언트 구현 담당이 구조 이해가 낮다 | B4와 B5를 C-A가 가져가고 C1을 C-B에게 맡긴다. 단 C1은 전투 코드 지식이 필요해 **정답지가 약하므로 권장하지 않는다**. 대신 B4, B5의 결정 목록을 더 자세히 쓴다 |
| 서버 구현 담당이 여유가 있다 | B3를 S-B로 옮긴다(S-A의 부하 완화) |
| 클라이언트가 3명이 될 수 있다 | B5a-1과 B5a-2를 새 사람에게 준다(구현형, 정답지가 명확하다) |
| 서버 2명이 모두 설계 경험이 적다 | B2의 결정 목록을 더 구체적으로 쓰고 S-A가 코드 리뷰를 맡는다. C3는 정책 상수가 핵심이라 구현 전에 정책을 사람이 먼저 정한다 |

**이 영역에서는 바꾸지 않는 것:** 서버 작업을 클라이언트 담당에게, 클라이언트 작업을 서버 담당에게 옮기지 않는다. 영역을 넘는 일은 이해 비용이 크다.
