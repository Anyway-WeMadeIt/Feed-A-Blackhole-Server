## 한 줄 요약

"서버가 모든 것을 처리하고 클라이언트는 온라인에서만 결과를 받아 그린다"에서
**"클라이언트가 자기 진행도를 가지고 오프라인에서도 플레이하고, 서버는 행위 로그를 사후에 검증해 정본을 유지한다"** 로 바꾼다.

## 배경: 기존 방향과 왜 다시 보게 됐나

기존 방향(현재 api-spec의 전제):

- 서버가 원본이자 유일한 처리 주체이고, 노드 구매·진행 변경은 서버 요청으로만 일어난다.
- 오프라인 플레이는 허용하지 않는다(범위 밖으로 둠).
- 클라이언트는 원본 데이터를 가지지 않고, 서버가 가공한 필요한 정보만 받는다(숨겨진 노드의 존재·위치도 내려주지 않음).

다시 보게 된 이유는 두 가지이고, 둘 다 검토한 뒤 방향을 바꿨다.

### 1. 게임의 성격: 싱글 플레이에 온라인을 강제하는 비용

- 이 게임은 **싱글 플레이 인크리멘탈 게임**이다. 서버를 두는 목적은 진행도 보호와 랭킹이지, 모든 상호작용에 서버가 필요해서가 아니다.
- 모든 조작을 온라인 요청으로 강제하면 네트워크 상태가 곧 플레이 가능 여부가 된다. 싱글 플레이 게임에서는 사용성 비용이 과하다.
- 서버를 두면서 오프라인을 허용하는 방식(로컬 진행도 + 행위 로그 + 사후 검증)은 싱글 플레이 게임에서 보편적으로 쓰이는 절충이다.

### 2. 작업 흐름: 클라이언트에서 만든 것을 지우고 서버에서 다시 쓰는 오버헤드

서버가 유일한 처리 주체이려면, 클라이언트에서 이미 구현된 게임 로직을 **걷어내고 서버에서 다시 작성**한 뒤 클라이언트는 그 결과를 받는 구조로 **다시 바꿔야** 한다. 이는 같은 기능을 두 번 만드는 것이고, 클라이언트 구조를 두 번 바꾸는 것이다.

이 방식이 정당하려면 처음부터 서버와 함께 개발해야 한다. 클라이언트를 먼저 만든 뒤 서버로 옮기는 흐름에서는 맞지 않는다.

이 프로젝트는 클라이언트가 먼저 개발된 상태이므로, **"클라이언트 먼저 개발 → 서버 역할을 추가"** 하는 흐름에 맞는 구조가 더 자연스럽다. 로그 기반 사후 검증은 이 흐름에 맞는다.

| | 서버 단독 처리 | 로그 제출 + 서버 검증 |
|---|---|---|
| 클라이언트 | 기존 로직을 제거하고 서버 응답을 그리는 구조로 재작성 | 기존 로직 유지. 행위 로그를 기록해 서버로 보내는 기능만 추가 |
| 서버 | 게임 로직 전체를 다시 구현 | 게임 로직을 구현하지 않고 **검증에 필요한 규칙만 정의** |
| 클라이언트-서버 계약 | 요청/응답 API 전반 | 로그 형식 |
| 조정 여지 | 낮음 (전부 구현해야 동작) | 높음. 검증 수위(개연성 검사 → 재생 검증)에 따라 서버 부담을 **유연하게 조절** |

서버에서 구현할 규칙의 양은 검증 수위에 따라 달라지며, 필요한 콘텐츠에만 수위를 올릴 수 있다([검증 수위](#검증-수위)).

두 이유가 합쳐진 결론: 서버는 **정본을 보관하고 검증하는 역할**로, 클라이언트는 **게임을 실행하고 행위를 기록하는 역할**로 둔다.

## 목표와 비목표

**목표**

- 오프라인에서도 PvE 진행(노드 구매, 전투, 결산)이 가능하다.
- 서버는 모든 계정의 진행도 **정본**을 가지고, 규칙에 어긋난 진행도가 정본에 들어오지 않게 한다.
- 조작의 **비용을 올리고 비현실적인 값을 걸러내는** 수준의 보호를 한다.

**비목표**

- 조작을 불가능하게 만드는 것. 로그도 클라이언트가 만들므로, 규칙을 아는 사람이 규칙에 맞는 가짜 로그를 만드는 것은 막을 수 없다. 이를 전제로 한다.
- 오프라인 중에 단일 기기 로그인을 강제하는 것(연결이 없으면 강제할 수 없다. 동기화 시 분기 처리로 보완한다).

## 핵심 원칙

1. **서버는 모든 사용자의 진행도 정본을, 클라이언트는 자신의 진행도 사본을 저장한다.**
2. **클라이언트는 모든 행위를 로그로 기록한다.** 대표적으로 노드 구매, 전투 결산. (전투 중 행동까지 기록하는 수위는 보류)
3. **로그가 원본이고 진행도는 파생값이다.** 서버는 클라이언트가 보낸 진행도를 믿지 않고, 서버 상태에 로그를 적용해 얻은 결과와 비교한다.
4. **검증은 서버가 장부로 다시 계산하는 수준까지 한다.** 구매는 규칙으로 정확히, 전투는 처치 장부와 공급 상한 같은 개연성으로 검증한다(이벤트 단위 검증은 보류).
5. **온라인 전용 기능은 없다.** 랭킹과 도전과제는 조건부 후속이며, 구현한다면 검증된 서버 상태에서 서버가 계산한다.

## 대략적인 동작

### 동기화

- 온라인이면 행위를 **실시간으로** 서버에 제출한다.
- 오프라인이면 로그를 **축적**해 두었다가 서버에 연결되는 시점에 제출한다. 재연결 트리거는 재접속이 기본이고, 오프라인 중 일정 주기로 연결을 시도하는 방식도 검토한다.
- 제출 내용: 로그 + 현재 진행도(+ 이 로그가 기준으로 삼은 서버 버전).

### 서버 판정

```
제출된 진행도 == 서버 진행도        → 별도 검사 없음
제출된 진행도 != 서버 진행도        → 로그를 검사
  로그가 모두 유효                  → 통과. 서버 정본을 클라이언트에 맞춰 갱신
  유효하지 않은 로그가 있음          → 클라이언트 진행도를 서버(유효한 지점)에 맞춰 되돌림
```

- 되돌리는 범위는 **첫 무효 로그 직전까지 적용하고 이후는 폐기**하는 쪽으로 기울어 있다(로그가 앞 로그에 의존하므로 일부만 골라 적용하기 어렵다). 확정은 아니다. 서버 정본 그대로로 되돌리는 안도 있다.
- 되돌릴 때는 무엇이 왜 취소됐는지 클라이언트가 유저에게 알려야 한다. 조용히 되돌리지 않는다.

### 단일 기기와 갈라진 로그

- 한 계정은 **동시에 한 기기에서만 로그인 상태**여야 한다. 새 기기에서 로그인하면 기존 세션은 무효가 된다. **(보류: 구현하지 않는다. 게스트 계정은 자격이 기기에 묶여 같은 계정이 두 기기에 있기 어렵고, 갈라진 로그는 아래 규칙으로 정리된다. 설계는 archive 4장.)**
- 오프라인에서는 이 제약이 강제되지 않으므로, 두 기기가 같은 기준 버전에서 갈라져 로그를 올릴 수 있다. 이때 **한쪽만 채택하고 나머지는 버린다.** 서버의 현재 버전보다 낮은 기준 버전에서 시작한 로그는 분기로 보고 거절하는 것이 기본 방식이다(이미 있는 `revision` / `baseRevision`과 같은 개념으로 확장할 수 있다).
- 먼저 도착한 쪽을 채택하면 오래 오프라인으로 플레이한 쪽이 지는 경우가 생긴다(정직한 유저의 손실). 완화책으로 "이 기기가 이 버전부터 오프라인 진행 중"을 서버에 알려 다른 기기 로그인 때 경고하는 방법이 있다. 필요해지면 추가한다.

### 검증 수위

| 대상 | 수위 | 비고 |
|---|---|---|
| 노드 구매 | 규칙 검증 (비용, 선행 조건, 보유 Gold, Rank 범위) | 구매 자체는 규칙으로 판정 가능 |
| 전투 결산 | **L1**: 시작 스냅샷 대조, 처치 장부(Gold, EXP), 결산 규칙, 공급 상한, 시간 상한 | 서버가 장부로 다시 계산한다. 공급 상한 안에서의 처치 속도 조작은 막지 못한다 |
| 전투 중 이벤트 | (보류) 이벤트를 기록해 서버가 전투 흐름을 따라감 | archive 2장 |

랭킹 제출은 일반 진행도 동기화를 끝내 서버 정본이 최신임을 확인한 **뒤에** 받는다. 검증되지 않은 진행도로 만든 기록이 랭킹에 들어가지 않게 하기 위해서다.

## 마스터 데이터(노드 콘텐츠)의 위치

- 오프라인 플레이를 하려면 **클라이언트도 노드 규칙(비용, 효과, 해금 조건, 배치)을 가져야 한다.** 따라서 "클라이언트에서 원본을 가린다"는 목표는 버린다. 데이터는 비밀이 아니다.
- **같은 정보가 양쪽에 있고 일치해야 한다.** 전투 콘텐츠는 Unity 에셋을 정본으로 JSON으로 내보내 서버 저장소에 두고, 노드 콘텐츠는 서버의 CSV와 클라이언트 사본을 맞춘다([node-content.md](../node-content.md)). 전투 콘텐츠의 일치는 JSON의 **번들 해시**로 확인한다. (서버 JSON을 정본으로 하고 Unity에서 편집하는 방향은 보류, archive 5장.)
- **노드 데이터를 서버로 옮기는 작업 자체는 그대로 유효하다.** 의미만 "서버 전용 데이터"에서 "양쪽이 가진 같은 데이터"로 바뀐다.
- `battle` 엔트리는 그 판이 쓴 전투 콘텐츠의 해시를 선언하고, 서버는 현재 해시와 다르면 거절한다. 콘텐츠를 바꾸면 서버를 먼저 배포한다. (옛 버전의 규칙으로 검증하는 이력 보관은 보류, archive 6장.)

## 주의할 점과 미결 사항

- **규칙 구현이 두 곳에 있게 된다.** 서버는 Java(Spring Boot), 클라이언트는 C#(Unity)이므로 코드를 공유할 수 없다. 구매·해금 규칙과 스탯 계산이 양쪽에서 같은 결과를 내도록 하는 방법이 필요하다(예: 같은 데이터에 대한 공유 테스트 벡터, 서버 테스트로 클라이언트 기대값 고정). 이미 `RealNodeContentTests.CLIENT_STAT_IDS`처럼 계약을 테스트로 고정하는 방식을 쓰고 있다.
- 서버 검증과 클라이언트 계산이 어긋나면 정상 유저가 롤백되는 오탐이 생긴다. 오탐을 줄이는 것이 이 구조의 가장 큰 운영 리스크다.
- 전투를 얼마나 결정적으로 재현할 수 있는지는 랭킹 검증 범위를 정하는 전제 조건이다.

미결 사항:

1. 로그 엔트리 형식 (순번, 종류, 내용, 데이터 버전, 시각, 해시 연결 여부 등)과 서버 상태 모델(버전, 마지막 적용 순번, 활성 세션, 상태 해시).
2. 무효 로그 발견 시 되돌리는 범위 (첫 무효 직전까지 적용 vs 서버 정본 유지).
3. 동기화 API의 형태. 온라인 실시간 제출과 오프라인 일괄 제출을 같은 요청 형식으로 묶을 수 있는지.
4. 현재의 `POST /me/nodes/{id}/purchase`, `PUT /me/progress`의 운명 (아래 참고).
5. 일반 전투 결산의 개연성 검사 기준값, 랭킹 전투의 결정성 확보 방법.
6. 오프라인 진행 중 재연결 시도 주기, 분기 거절 시 폐기될 로그의 로컬 보관 여부.
7. 서버 규칙과 클라이언트 규칙의 일치를 어떻게 보장할지.

## 그대로 유지되는 것

- 서버가 모든 사용자의 진행도 정본과 노드 데이터 원본을 가진다.
- 노드 콘텐츠를 서버 저장소의 파일로 관리하고 시작할 때 검증해 불변 객체로 보관한다.
- 노드 ID는 바꾸지 않는다. `nodeContentVersion`, `revision` 같은 버전 개념.
- 게스트 인증(등록, 로그인, 토큰 갱신)의 틀.
- 서버가 정산·검증의 최종 결정권을 가진다는 원칙(검증 시점만 사후로 이동).
