## 0. 제외 경위

- 조건: 작업 가능 기간 10일, 4명, "무리하더라도 프로젝트를 완성"해야 한다. 후속 단계가 없으므로 **제외는 곧 구현하지 않는다**는 뜻이다.
- 작업을 일수로 환산하면 전체 약 73인일이고, 4명 × 10일은 40인일(무리하면 50)이다. 필수 범위만으로도 약 41인일이 든다.

## 2. L3 이벤트 검증

### 2.1 왜 L3였나

- **L1(결산 요약)** 만으로는 버프 때문에 상한이 느슨하다. 달 버프는 공격 속도와 범위를, 혜성 버프는 치명타 배율을 크게 올려서 이론상 dps 상한이 기본 스펙의 몇 배가 된다.
- **L2(적별 집계 레코드)** 를 거쳐 가는 안도 검토했다. 합계와 개수로 풀리는 검사는 L2도 거의 다 하지만, 버프의 **시간 구간**(어느 Tick에 몇 스택이 있었는가)과 짧은 시간의 몰림은 알 수 없어서 버프 때문에 상한이 느슨한 문제를 풀지 못했다. 그래서 L2는 만들지 않고 L1과 L3로 가기로 했다.
- L3는 전투 중 이벤트(생성, 타격, 처치, 버프, 효과)를 순서대로 기록해 서버가 전투 흐름을 장부로 따라가는 방식이다. **위치와 이동은 추적하지 않는다.**

### 2.2 모델 원칙

- 클라이언트는 **관측한 사실**(생성, 타격, 처치)만 기록하고, 계산할 수 있는 효과는 서버가 규칙으로 도출한다. 예: 버프 활성은 "달이 처치됨"에서 서버가 구간을 계산한다.
- 위치 의존적인 것(연쇄 번개의 대상 선택 등)은 클라이언트가 보고하고 서버는 개수, 시점, 피해량만 확인한다.
- 이벤트 종류와 필드, 시간 모델은 아래 2.7을 따른다.

### 2.3 적 생성 규칙 (D-9)

적은 판 도중에도 생성되며, 모든 생성은 이벤트로 기록한다. 코드(`EnemySupply`, `DeathBonuses`)를 확인한 결과 생성 경로는 **네 가지**다.

| 원인 (`cause`) | 규칙 | 서버가 확인하는 것 |
|---|---|---|
| `START` 시작 공급 | 판 시작(0초)에 종류별 고정 수 | 종류와 수량이 콘텐츠와 일치 |
| `GROWTH` 레벨업 | 블랙홀 Level이 오를 때마다 정해진 종류와 수. 한 Step에 여러 Level이 오르면 그만큼 | 서버가 처치 EXP 합과 `levelExp` 사다리로 Level업 횟수를 계산하고, 기대 수량과 **정확히** 일치해야 한다 |
| `RESPAWN` 사망 재생성 | 일반 적(픽업 제외)이 죽을 때 `RespawnChance` 확률로 **같은 종류** 1마리 | 각 생성은 어느 사망에서 나왔는지 참조한다. 한 사망당 최대 1마리, 같은 종류여야 한다 |
| `PERIODIC` 주기 출현 | **혜성만** 해당한다. `SpawnPeriod`마다 `SpawnChance` 확률로 1마리, `RainChance`로 `RainCount`마리가 한꺼번에 나온다. 혜성은 적이 아니라 **버프 획득용 파괴 오브젝트**다(HP 1, Gold 0, EXP 0) | 생성 수 ≤ ⌊경과 시간 ÷ 주기⌋ × `RainCount`. 서버는 혜성도 다른 적과 같은 `spawn`/`kill` 이벤트로 처리한다 |

생성 이벤트 초안 (위치는 검증하지 않으므로 싣지 않는다):

```json
{ "t": 1520, "id": 57, "kind": "Asteroid", "tier": 2, "trait": null, "size": 1,
  "cause": "RESPAWN", "ref": 41 }
```

`ref`는 원인에 따라 다르다: `GROWTH`는 도달한 Level, `RESPAWN`은 죽은 적의 ID, `START`와 `PERIODIC`은 없다.

**함께 알아 둘 것**

- **시간 추가(`TimeChance`)도 사망 시 확률 효과다.** 죽을 때 확률로 제한 시간이 늘어나고, 이는 `playedSeconds ≤ 제한 시간 + 연장`을 검증하는 근거가 된다. 사망 이벤트에 성공 여부를 기록해야 한다.
- **적 1마리의 Tier, 성질, 크기는 생성 시 `QuotaPicker`가 정한다.** 이 값이 HP, Gold, EXP와 사망 효과를 결정하므로 생성 이벤트에 실어 서버가 규칙 범위를 확인해야 한다. 성질은 동시 상한(`MaxActive`)이 차면 붙지 않으므로 서버가 살아 있는 성질 수를 추적한다.
- **일반 적의 안전 상한 1000마리.** 생성 요청이 여유를 넘으면 초과분은 만들어지지 않는다. 서버는 기대 수량을 `min(요청 수, 여유)`로 계산한다.

**생성 검증의 세 단계**

1. **구조 검증:** 원인 연결, 종류 일치, 수량 상한, 동시 상한.
2. **확률 검증(통계):** `RESPAWN`, `PERIODIC`, 시간 추가, 치명타의 발생 횟수가 이항 분포 범위 안인지 본다. 판 단위로는 넓게, 계정 누적으로는 좁게 잡는다. 범위는 섀도 모드의 실제 데이터로 보정한다.
3. **난수 재현(정확 검증, 선택):** 2.6을 따른다.

### 2.4 전투 규칙과 검증 방식 (D1 조사 결과)

합의한 내용과 코드(`BreakerSkill`, `DeathBonuses`, `DeathEffects`, `GameSession`, `World` 등)를 확인한 결과다.

**검증하지 않는 것 (결정됨).** 적과 브레이커의 위치와 이동, 생성 위치, **타격이 실제로 범위 안에 있었는지**, 한 Tick에 몇 마리가 범위에 들었는지. 매 프레임 위치를 기록하고 검증하는 것은 비용에 비해 과하다고 판단했다.

**1. 브레이커 Tick과 타격 피해: 공식이 결정적이다.**

- Tick마다 범위 안의 모든 적에게 피해를 준다. 피해 = (기본 피해 + 대상이 행성/별일 때 추가 피해) × (치명타면 `1 + 치명타 피해`, 아니면 1).
- 치명타 피해 = 기본 치명타 피해 × (1 + 혜성 스택 수 × 스택당 보너스). 치명타 여부는 **Tick 하나에 하나**이고 그 Tick의 모든 대상이 공유한다.
- 혜성 스택이 하나라도 있으면 그 Tick은 확정 치명타다. 공격 속도 = 기본 × (1 + 달 스택 수 × 스택당 속도 보너스).
- 모든 수치는 노드 업그레이드가 정하므로 서버가 전투 시작 스탯 표에서 계산할 수 있다.
- 결론: **타격 피해량은 "상한"이 아니라 정확한 값으로 검증된다.**

**2. 버프 스택** (`BreakerSkill.cs`)

- 달과 혜성을 처치할 때마다 항상 1스택을 얻는다. **스택마다 독립적인 지속 시간**을 가지며, 새 스택이 기존 스택의 시간을 갱신하지 않는다.
- 서버는 달/혜성 사망 이벤트로 스택 목록을 만들고 지속 시간이 지나면 뺀다. 이것으로 각 Tick 시각의 스택 수가 정해진다.
- 버프 시간은 Tick 뒤에 줄어든다. 스택이 끝나는 Step의 Tick까지는 효과가 있으므로 만료 경계에서 한 Step만큼 오차를 허용한다.
- 달의 공격 범위 증가(반지름 최대 2배)는 위치와 관련되어 검증하지 않는다.

**3. 치명타 난수** (`BreakerSkill.cs:142`, `:172`)

- 확정 치명타(혜성 스택 있음)이거나 확률 ≥ 1이면 난수 없이 치명타, 확률 ≤ 0이면 난수 없이 일반 타격, 그 외에는 **Tick당 난수 1회**다. 난수는 **대상이 1명 이상인 Tick에서만** 굴린다.
- 서버는 타격이 있었던 Tick을 알면 소비 횟수를 알 수 있고, 혜성 스택 상태를 정확히 추적하면 난수를 재현해 정확히 검증할 수 있다. 통계 검사로 시작해도 된다.
- 이벤트에 **Tick 번호, 시각, 대상 수, 치명타 여부**가 필요하다.

**4. 시간 추가와 제한 시간** (`DeathBonuses.cs:21`, `GameSession.cs:128`)

- 일반 적(픽업 제외)이 죽을 때마다 **재생성 확률과 시간 추가 확률 각각에 난수 1회**(확률이 0과 1 사이일 때). 사망 순간, 전체 사망 순서대로 소비한다.
- 제한 시간 = 기본 시간 + (오른 Level 수 × 블랙홀 성장 시간) + (시간 추가 성공 수 × `KillTimeBonus`). 모두 이벤트에서 계산되므로 `playedSeconds ≤ 제한 시간`을 정확히 검증한다.
- 이정표에 닿은 Step에서는 성장 공급과 생성 처리를 하지 않고 판이 끝난다(`World.cs:124`).

**5. 사망 효과** (`DeathEffects.cs`)

- 연쇄 번개와 레이저: 피해 = 효과 피해량 × (치명타면 효과의 치명 배율). 치명타는 **발동 한 번에 한 번** 판정하고 그 발동의 모든 적중이 같은 결과를 쓴다. 따라서 한 발동의 모든 적중은 치명 여부와 피해량이 같다는 불변식으로 검사한다.
- 슈퍼노바(폭발): 각 피격 대상의 **최대 체력 비례 피해**다. 서버는 대상의 최대 체력(종류, Tier, 크기)을 알고 있으므로 정확한 값을 검증한다.
- 최종 수치는 모두 노드 업그레이드가 정한다.
- 불변식: **성질이 붙은 특수 적은 사망 효과의 피해를 받지 않는다**(효과가 효과를 부르지 않는다). 효과 피해는 직전 사망 이벤트를 출처로 가져야 한다.
- **난수 소비는 위치와 무관하다.** 한 스트림(`RandomStream.DeathEffect`)을 번개와 레이저가 함께 쓴다.
  - 번개: 발동마다 갈래 판정(성공할 때까지, 최대 8줄기)과 치명타 판정 1회(치명 확률 > 0일 때). 대상 선택에는 난수가 없다(가장 가까운 적).
  - 레이저: 죽는 순간 방향 1회, 발사 때 치명타 1회(확률 > 0일 때). 폭발은 난수를 쓰지 않는다.
  - 한 Step 안의 처리 순서는 "예고가 끝난 레이저 발사 → 이번 Step의 사망 효과(사망 순서)"이고, 레이저는 죽은 뒤 0.4초 후 Step에서 발사되어 다른 효과와 시간상 섞인다. 정확 재현은 가능하지만 Step 단위 순서가 필요하므로 통계와 불변식으로 먼저 검사한다.
- **번개 대상 수의 상한은 계산이 쉽다.** 발동 하나의 적중 수 ≤ 줄기 수 × `maxTargets`, 줄기 수는 갈래 확률이 0이면 1, 아니면 최대 8. 기본값은 `electricAsteroid.chain` 3, `electricStar.chain` 5, 갈래 확률 0이다. 이벤트에 발동 ID가 있으면 이 검증을 적용한다.

**6. 달 동시 상한** (`moonPlanet.maxCount`, 기본 10)

성질을 붙이기 직전에 (살아 있는 같은 종류·성질 적 + Breaker에 남은 달 스택) ≥ 상한이면 성질이 붙지 않는다(`EnemySupply.cs:210-225`, `World.cs:140`). 죽은 적은 즉시 살아 있는 목록에서 빠진다(`EnemyRoster.cs:118`). 서버 검증식은 "성질이 붙은 생성 직전의 합 < 상한"이고, 상한 0은 제한 없음이다. 스택 만료가 Step 단위라 경계에서 ±1을 허용한다.

**7. 시간 모델** (`GameBootstrap.cs:127`, `BattleSystem.cs:80`, `ProjectSettings/TimeManager.asset`)

- Step 길이는 `Time.deltaTime`이라 프레임마다 다르다. Unity 설정 `Maximum Allowed Timestep`이 0.333초이고 코드는 delta를 따로 자르지 않는다. 큰 delta에서는 한 Step에 Tick이 여러 번 일어난다(`BreakerSkill.cs:89`).
- 그래서 **이벤트 시각은 Step이 끝난 뒤의 경과 시간**으로 기록해야 "n번째 Tick은 이 시각보다 빠를 수 없다" 검사가 안전하다. 공격 간격은 "n번째 Tick이 가능한 가장 이른 시각"(스택 이력 반영)을 계산해 비교하면 프레임 길이에 무관하다.
- 일시정지는 판을 진행하지 않으므로 경과 시간이 멈춘다. 이벤트 시각에 표현할 필요가 없다. 배속(`timeScale`)은 전투 코드에 없다.

**8. 순번 카운터가 따로다.** 피격(`EnemyRoster._nextHitSequence`), 사망(`_nextDeathSequence`), 사망 효과(`DeathEffects._nextSequence`)가 각각 별도로 늘어나서 서로의 순서를 알 수 없다. 이벤트 기록기가 **통합 순번**을 붙여야 한다.

**검증 정밀도 요약**

| 대상 | 방식 |
|---|---|
| 브레이커 타격 피해량 | 정확한 값 (공식, 허용 오차 내) |
| 처치 조건, Gold, EXP, Level업과 생성 | 정확 (누적 계산) |
| Tick 간격과 총 Tick 수 | 상한 (스택 이력 반영) |
| 버프 스택과 만료 | 정확 (시간 허용 오차) |
| 치명타 | 난수 재현 또는 통계 |
| 재생성, 시간 추가, 혜성 출현 | 난수 재현 또는 통계 |
| 사망 효과 피해 | 번개/레이저: 값은 정확, 치명타는 통계. 폭발: 정확 |
| 위치, 범위 안 여부, Tick당 대상 수 | **검증하지 않음** |

### 2.5 범위 기반 피해의 대상 수 (D-10)

적끼리 겹칠 수 있어서 **한 Tick에 동시에 맞힐 수 있는 수에 이론적 상한이 없다.** 위치를 검증하지 않는다는 결정의 직접적인 결과다.

| 피해 | 대상 결정 | 대상 수 검증 |
|---|---|---|
| 전기(연쇄 번개) | 정해진 규칙으로 대상을 찾는다 | **가능.** 발동당 줄기 수 × `maxTargets` 이하 |
| 브레이커 Tick | 범위 기반 | 이론 상한 없음 |
| 레이저 | 범위 기반 | 이론 상한 없음 |
| 폭발(슈퍼노바) | 범위 기반 | 이론 상한 없음 |

조작하는 쪽이 매 Tick "살아 있는 적 전부를 맞혔다"고 주장하면 처치 속도가 부풀려진다. 처치는 EXP, 제한 시간 연장, 적 생성으로 이어지므로 효과가 누적된다. 레이저와 폭발은 특수 적이 죽을 때만 일어나므로 노출이 브레이커보다 작다.

**위치 없이도 걸 수 있는 정확한 제약**

- 한 Tick에 같은 적은 한 번만 맞는다. 한 Tick의 타격 수 ≤ 그 시점에 살아 있는 적의 수(서버가 생성과 처치로 추적한다).
- 죽은 적과 아직 생성되지 않은 적은 맞을 수 없다. 사망 효과는 특수 적을 맞힐 수 없다.

**선택지**

| | A. 클라이언트 규칙으로 동시 타격 수를 제한 | B. 서버 검증 조건만 (넉넉한 상한) | C. 통계와 경험적 임계 (플래그) |
|---|---|---|---|
| 방식 | 게임이 한 Tick(또는 효과)에 맞히는 최대 수를 가진다. 서버는 그 값을 정확히 검증한다 | 서버가 상한을 넘으면 거절한다 | 판 단위 평균과 계정 누적 분포를 모아 이상치를 표시한다 |
| 오탐 | 없음(규칙 자체) | 상한이 낮으면 정상 플레이를 거절 | 거절하지 않으므로 없음 |
| 효과 | 상한까지의 부풀림을 차단. 상한이 크면 느슨 | 상한이 클수록 의미가 없다 | **평균 기준이라 최대 상한보다 훨씬 촘촘하게** 잡을 수 있다 |
| 비용 | 게임플레이 변경(밸런스, 반지름 노드의 가치), 대상 선택 규칙 정의, 클라이언트 작업 | 서버만 | 서버만. 판단은 사람이 한다 |

핵심은 **최대치보다 평균이 촘촘하다**는 점이다. 정상 플레이에서 Tick당 대상 수는 가끔 크게 튀어도 판 전체 평균(빈 Tick 포함)은 낮다. 판 단위 평균(Σ대상 수 ÷ Tick 수)을 반지름별로 비교하는 임계를 쓴다.

**권장 순서:** ① 정확한 제약을 적용하고 이벤트에 Tick별 대상 수와 효과별 대상 수를 기록하며 섀도 모드에서 분포를 수집한다. ② 정상 플레이의 최댓값이 충분히 낮으면 A를 도입하되 상한을 관측된 정상 최댓값보다 넉넉히 높게 잡는다. 그렇지 않으면 C로 운영한다. ③ A를 도입할 때는 상한 초과 시 어떤 적이 맞는가(조준점에 가까운 순을 권장), 상한을 반지름에 비례시킬지(예: 면적 비례), 노드 수치(`breaker.maxTargets`)로 둘지, 레이저와 폭발에도 적용할지를 정한다.

> 이 문제는 L1에서도 일부 남는다. L1은 이벤트가 없어 Tick 단위의 대상 수는 보지 못하고, 대신 **공급 상한**(처치 수 ≤ 생성된 적의 수)으로 처치 수 전체를 묶는다. 작업 분해의 C3를 참고.

### 2.6 난수 재현 (정확 검증, 선택)

`BattleRandom`은 시드와 용도(`RandomStream`)로 나뉜 정수 해시 난수이고, 스트림마다 소비 순서가 시간이나 위치가 아니라 **이벤트 순서**로만 정해진다. 서버가 시드와 이벤트 순서만으로 `Respawn`, `TimeBonus`, `PeriodicSpawn`, `Critical` 스트림을 재현하면 **"이 사망에서 재생성이 일어났어야 하는가"를 정확히** 확인할 수 있다.

- 조건: 난수 알고리즘을 Java로 옮긴다(정수 연산이라 언어 간 차이가 없다). 확률 비교는 float과 double의 경계 오차를 허용한다.
- Tier, 성질, 크기까지 재현하려면 적 구성 규칙(3장)이 서버에 필요하다.
- **시드는 클라이언트가 정하므로 유리한 시드를 고르는 것(시드 그라인딩)은 막지 못한다.** 보호 수준상 수용한다. 필요해지면 서버가 동기화 때 시드 묶음을 발급해 순서대로만 쓰게 하는 확장이 가능하다(6장).
- 권장: 구조 검증과 통계 검증을 먼저 만들고, 정확 재현은 섀도 모드 결과를 보고 도입한다.

### 2.7 이벤트 기록과 형식 요구 (D2, D3)

- 기존 `HitRecord`(적 ID, 종류, Tier, 피해량, 치명타 여부, 피해 소스, 순번), `DeathRecord`, `BreakerTick`을 원재료로 쓴다. **시간 필드가 없다.**
- 모든 이벤트에 **통합 순번과 Step 번호**를 붙이고, 시각은 **Step이 끝난 뒤의 경과 시간**으로 기록한다(전투 시작 기준 정수 ms).
- 사망에는 시간 추가 성공 여부를, **생성**에는 원인과 참조를, 번개 적중에는 **발동 ID**를 붙인다. 위치와 연출용 값은 보내지 않는다.
- 이벤트는 미리 확보한 구조체 버퍼에 쓰고(모바일 GC 끊김 방지), 직렬화는 전투 중이 아니라 결산 화면에서 한다. 로컬에 최근 N판의 trace를 링버퍼로 보관한다(서버가 정상 판을 잘못 거절했을 때 재현하는 용도).
- 수치는 서버가 상대 오차를 허용한다. 시간 경계(버프 만료, 공격 간격, 주기 출현)에는 허용 오차를 두며, 크기는 프레임 길이 상한(실기기 delta 실측 필요)을 따른다.

### 2.8 서버 검증 단계와 보조 작업

- **D4 L3 검증기(단계적):** ① 생성(원인 연결, 수량 상한), 타격, 처치, Gold 합계, 위치 없이 걸 수 있는 정확한 제약 → ② 연쇄 피해의 인과와 확률 효과의 통계 검사 → ③ 버프 구간과 시간 의존 검사, (선택) 난수 재현.
- **D5 골든 트레이스:** 클라이언트가 실제 판의 trace를 내보내는 도구를 만들고, 서버 테스트가 그 trace를 전부 통과시키는지 확인한다. 클라이언트 규칙이 바뀌고 서버가 따라가지 않으면 CI에서 실패한다.
- **D6 섀도 모드:** 서버가 L3를 검증하되 거절하지 않고 불일치만 기록한다. 불일치 조회와 강제 전환 기준. **동시 타격 수 분포 수집**(반지름별 Tick당 대상 수, 판 평균, 효과별 대상 수)과 D-10 결정용 리포트. 오탐(정상 유저의 롤백)이 가장 큰 운영 위험이므로 강제 전환의 선행 조건이다.

### 2.10 trace 전송 설계

- `battle` 엔트리의 `trace` 필드에 같은 요청으로 싣는다(JSON, gzip 본문 허용). 크기가 문제되면 별도 업로드로 분리한다.
- 오프라인으로 쌓인 판이 많으면 trace가 수 MB가 될 수 있으므로 gzip, **판 단위 분할 전송**(한 엔트리의 trace는 나누지 않음), 이어 보내기를 지원한다. Wi-Fi일 때 우선 전송하는 정책도 검토한다.
- 항상 업로드하는 안(단순)과 의심 계정에만 서버가 요청하는 안(업로드는 작지만 요청 흐름이 생김)이 있었고, 항상 업로드를 권장했다. 이 경우 L1 필드는 L3에서 계산한 값과의 대조용 주장값이 된다.

### 2.11 L3를 위해 필요했던 확인 사항

1. 실기기(저사양 안드로이드 포함)의 `Time.deltaTime` 최댓값(앱 백그라운드 복귀 포함).
2. 노드 수치 60개가 전투 규칙의 어디에 쓰이는지 대응표.
3. 시드가 `Environment.TickCount`인 것이 의도인지(`BattleSystem.cs:60`).
4. 전투 중 앱 종료나 크래시는 그 판을 기록하지 않는다(기존 규칙). 모바일에서는 전투 중 백그라운드로 가도 자동 일시정지가 없다.

## 3. 적 구성 규칙의 완전 이식 (C4 전체)

시작 공급 수, 성장 공급 수, 색 비율, 성질 확률, 크기, 재생성과 시간 추가 확률은 모두 **노드 수치 값에서 계산되는 규칙**이다. 위치는 `GameSessionFactory.cs`(변환 사슬: 소행성 → 행성 → 별, 성장 공급 % 반올림), `EnemyComposition.From`, `EnemyUpgradeStats`, `MassRule`(질량 → 색 비율), `SizeRule`, `HqUpgradeStats`다.

- **L1에서 쓰는 부분(C4a, C4b)** 은 작업 분해에 있다: 시작 공급과 변환, 성장 공급, 색 비율의 **허용 범위**(어느 Tier가 나올 수 있는가), 크기, 성질 확률, 재생성 확률로 공급 상한을 계산한다.
- **완전 이식**은 여기에 더해 `QuotaPicker`(누적 몫 선택기)와 `BattleRandom`을 Java로 옮겨 **생성될 적의 Tier, 성질, 크기를 순서대로 재현**하는 것이다. L3의 난수 재현(2.6)과 생성 이벤트 검증(2.3)의 전제다.
- 정확 재현의 범위(색 비율, 크기까지 할지)는 조사 후 정한다. 약 3인일이 추가로 든다.

## 4. 단일 기기 로그인 (B6)

한 계정은 **동시에 한 기기에서만** 로그인 상태일 수 있다.

- 로그인할 때마다 서버가 **세션 ID(`sid`)** 를 새로 만들어 계정의 현재 세션으로 저장하고, 이전 세션의 리프레시 토큰을 모두 폐기한다.
- 액세스 토큰에 `sid`가 들어가고, 서버는 인증이 필요한 모든 요청에서 `sid`가 계정의 현재 세션과 같은지 확인한다(작은 조회 1회). 다르면 `401 SESSION_REPLACED`다.
- 리프레시 토큰은 발급된 세션에 묶인다. 교체된 세션의 리프레시 토큰이 들어오면 **다른 토큰을 건드리지 않고** `401 SESSION_REPLACED`를 낸다. 현재 세션 안에서 이미 쓴 토큰이 다시 들어오는 경우만 재사용 감지(그 세션의 모든 토큰 폐기)가 동작한다. 그렇게 하지 않으면 교체된 기기의 옛 토큰이 새 기기의 토큰까지 지워 버린다.
- **자동 재로그인 규칙:** `INVALID_REFRESH_TOKEN`(만료, 없는 토큰)은 자격으로 자동 재로그인한다. **`SESSION_REPLACED`는 자동 재로그인하지 않는다.** "다른 기기에서 로그인되었습니다. 이 기기에서 계속하시겠습니까?"를 묻고, 확인하면 로그인한다. 자동 재로그인을 하면 두 기기가 서로를 쫓아내는 일이 반복된다.
- 게스트 계정은 자격이 기기에 묶여 있어, 같은 계정이 두 기기에 있으려면 백업 복원이나 복제가 필요하다. 이때의 낡은 로컬 진행은 동기화에서 `BASE_MISMATCH`로 서버 상태에 맞춰진다(서버가 더 앞서 있는 한 손실이 없다).
- 오프라인 중에는 이 제약을 강제할 수 없다. 두 기기가 갈라져 진행한 로그는 동기화에서 한쪽만 채택된다. 먼저 도착한 쪽을 채택하면 오래 오프라인으로 플레이한 쪽이 지는 경우가 생기므로, 완화책으로 "이 기기가 이 버전부터 오프라인 진행 중"을 서버에 알려 다른 기기 로그인 때 경고하는 방법이 있다.
- 작업: B6 — 새 로그인 때 이전 세션 무효화, 동기화 요청에서 세션 확인, 클라이언트의 "다른 기기에서 로그인됨" 처리(C+S, M, 선행 B2).

## 5. 데이터 정본 방향 X (서버 JSON 정본)

이번 프로젝트는 **Unity 에셋을 정본으로 하고 JSON으로 내보내 서버 저장소에 두는 방향(Y)** 을 택했다. 아래는 처음 합의했던 방향 X(서버 저장소의 파일이 정본이고 Unity에서 편집)의 설계다.

### 5.1 구조

```
[정본] 서버 저장소 content/ (JSON, CSV) ── 동기화 도구 ──▶ [클라이언트] StreamingAssets/content/ (생성물, 읽기 전용)
   │  version = 파일 바이트의 SHA-256                         │  ContentData JSON → 기존 ContentLoader (변경 없음)
   ▼                                                          ▼
[서버] 시작 시 로드·검증, 과거 버전 보관                   로그 엔트리에 contentVersion을 실어 전송
```

- 교환 형식은 `ContentData`(클라이언트 `Core` 어셈블리의 직렬화 가능한 DTO)의 JSON이다. 표현 데이터(색, 스프라이트)는 DTO에 없어서 에셋 쪽에 남고 ID로 연결한다.
- 노드와 전투 콘텐츠의 번들 버전을 하나로 합친다(D-2). 기존 `nodeContentVersion`은 노드 목록 캐시용으로만 유지한다.
- 과거 버전의 번들은 배포 때 버전 이름의 폴더로 불변 보관하고 최근 N개만 유지한다(D-3). 오프라인으로 옛 버전을 쓴 로그를 **그 버전의 규칙으로** 검증하기 위해서다.
- 번들 버전은 파일 바이트의 SHA-256이다. Windows에서 CRLF와 LF가 섞이면 바이트가 달라지므로 `.gitattributes`에 `*.json text eol=lf`를 두거나 해시 전에 줄바꿈을 정규화한다.

### 5.2 작업

| ID | 작업 | 영역 | 규모 |
|---|---|---|---|
| A4 | 클라이언트 JSON 콘텐츠 생산자: JSON을 읽어 `ContentData`를 만들어 기존 로더에 연결하고, 표현 에셋을 시각 전용으로 분리해 ID로 연결 | C | M |
| A5 | Unity 에디터 도구(5.3) | C | L |
| A6 | 클라이언트 사본 동기화와 일치 검사 CI | C+S | M |
| A7 | 노드 콘텐츠도 같은 체계로 통합: 클라이언트 `NodeTable` 동결을 풀고 사본을 생성물로 바꿈 | C+S | M |
| A3(전체) | 번들 버전과 버전 저장소(이력 보관 포함) | S | M |

### 5.3 A5 에디터 도구 설계: Unity에서 서버 저장소 값을 읽고 올리는 방법

서버가 파일을 정본으로 쓰고 시작 시 한 번만 읽으므로(`../node-content.md`: 콘텐츠 변경은 재배포가 필요하다), Unity에서 "올린다"는 **서버 저장소의 파일을 고치는 것**이다. 서버를 호출하는 것이 아니다.

```
1. 설정   : Editor 사용자 설정(EditorPrefs, 커밋하지 않음)에 서버 저장소의 로컬 체크아웃 경로
2. 읽기   : 도구가 <서버>/src/main/resources/content/** 를 읽어 편집 버퍼에 로드
3. 편집   : ContentData를 담는 저장하지 않는 임시 ScriptableObject를 기본 인스펙터로 편집.
            ContentLoader 진단을 편집 중에 화면에 표시
4. 저장   : 정해진 서식(정렬, 들여쓰기, LF, 숫자 표기)으로 서버 체크아웃에 JSON을 쓰고,
            클라이언트 사본도 같은 내용으로 다시 만든다. 번들 버전을 화면에 표시
5. 반영   : 사람이 서버 저장소에서 브랜치 → 커밋 → PR → CI 검증 → 병합 → 배포
            (클라이언트 저장소에도 사본 변경을 커밋)
```

- git 자체는 도구가 다루지 않는다(자격 증명과 충돌 처리가 복잡해진다). 파일을 정확히 쓰는 것까지가 도구의 책임이다.
- 서식을 고정하지 않으면 저장할 때마다 불필요한 diff가 생기므로, 정렬과 숫자 표기가 같은 출력(canonical writer)이 필요하다.
- 모든 편집자가 서버 저장소를 로컬에 체크아웃해야 한다.
- 대안인 GitHub API 직접 커밋(토큰 관리 필요)과 서버 관리 API(정본이 git이라는 원칙과 재배포 필요성에 어긋남)는 권장하지 않았다.
- **완료 조건:** Unity에서 값을 바꾸고 저장 → 서버 저장소의 파일과 클라이언트 사본이 모두 갱신 → 서버 테스트와 클라이언트 로더가 통과.

### 5.4 왜 Y를 택했나

| | X. 서버 JSON 정본 | **Y. Unity 에셋 정본(채택)** |
|---|---|---|
| 편집 | JSON 직접 편집 (A5 없이는 불편) | 지금처럼 인스펙터로 편집 후 내보내기 메뉴 실행 |
| 서버 | JSON 파일이 정본 | 내보낸 JSON을 서버 저장소에 커밋(사본) |
| 일치 보장 | 번들 해시 | 번들 해시(같음). 내보내기를 깜빡하면 새 클라이언트의 로그가 거절되어 바로 드러남 |
| 추가 작업 | A4 로더, A5 도구 | 내보내기 메뉴 하나 |

아직 폴리싱 단계라 밸런스를 만질 가능성이 높고, 인스펙터를 쓰는 기존 워크플로를 깨지 않는 것이 중요했다. "한 곳에서만 편집하고 다른 쪽은 생성물"이라는 원칙은 그대로 지킨다.

## 6. 동기화의 부가 설계

| 항목 | 설계 | 제외한 이유 |
|---|---|---|
| **gzip과 분할 전송** | 요청 본문 `Content-Encoding: gzip` 허용. 한도 초과 시 `413`, 클라이언트가 묶음을 반으로 나눠 재시도. 한 엔트리의 `trace`는 나누지 않음 | trace가 없으면 본문이 수 KB |
| **재시도 가능 거절**(`retry: true`) | 서버가 모르는 최신 `contentVersion`은 `CONTENT_VERSION_UNKNOWN`(retry true)으로 거절하고, 클라이언트는 적용된 앞부분만 빼고 나머지를 보관해 나중에 다시 보낸다. 클라이언트 릴리스가 서버 배포보다 앞선 상황에서 로그를 잃지 않기 위함 | 서버를 먼저 배포하는 운영 규칙으로 대체. 모든 거절은 영구(`retry` 없음) |
| **콘텐츠 이력** | `CONTENT_VERSION_EXPIRED`(보관 기간을 넘긴 옛 버전). 서버가 최근 N개 버전을 보관(D-3) | 현재 버전만 검증 |
| **`GET /system/status`** | `{ minClientVersion, maintenance, latestContentVersion, supportedContentVersions }`. 클라이언트가 자기 번들의 버전이 목록에 없으면 업데이트를 안내하고, 최신이 아니면 오프라인 진행의 위험을 알린다 | 운영 편의 |
| **`429 RATE_LIMITED`** | 요청이 너무 많음. `Retry-After`를 따른다 | 운영 편의 |
| **서버 발급 시드 묶음** | 동기화 때 서버가 시드 묶음을 발급해 순서대로만 쓰게 하여 시드 그라인딩을 막는다 | 보호 수준상 수용 |
| **오프라인 진행 선언** | "이 기기가 이 버전부터 오프라인 진행 중"을 서버에 알려 다른 기기 로그인 때 경고(분기로 인한 정직한 유저의 손실 완화) | B6와 함께 제외 |

## 7. 후속 API 스케치

필수 범위의 진척을 보고 5일차에 조건부로 결정하는 항목이며, 구현하지 못하면 이 스케치가 기록으로 남는다. 랭킹과 도전과제는 **검증을 통과한 서버 상태에서 서버가 직접 계산**하며, 클라이언트가 점수나 달성 여부를 주장하는 방식은 쓰지 않는다.

| | 경로 | 설명 | 규모 |
|---|---|---|---|
| POST | `/me/ranking` | 닉네임과 함께 랭킹 등록을 요청한다. 서버는 먼저 밀린 로그의 처리가 끝났는지(마지막 동기화의 `revision`과 일치) 확인한 뒤 검증된 진행도로 점수를 계산한다. 닉네임 유일성 제약 | 약 3인일 |
| GET | `/rankings` | 랭킹 조회 | |
| GET | `/achievements` | 도전과제와 전체 유저의 달성률. 서버가 `battle` 엔트리의 `kills`를 누적 통계로 저장하고 달성을 계산한다 | 약 3인일 |
| POST | `/auth/link` | 소셜 로그인 연동. 모바일에서는 기기 변경과 재설치로 게스트 자격을 잃기 쉬워 우선순위가 높다 | |
| GET | `/content/{version}` | 콘텐츠 번들 런타임 다운로드 | |

## 8. 모바일 고려 중 L3 관련분

범위 안의 모바일 고려(로그 즉시 영속 저장, 재시도, float 오차, 기기 변경)는 작업 분해에 있다. 아래는 L3와 함께 제외된 것이다.

| 영향 | 내용 |
|---|---|
| 수집 시 메모리 할당 금지 | 모바일의 GC 끊김은 전투 체감에 직접 영향을 준다. 이벤트는 미리 확보한 구조체 버퍼에 쓰고, 직렬화와 압축은 전투 중이 아니라 결산 화면에서 한다. 저사양 기기에서 프레임 영향을 실측한다 |
| 데이터 사용량 | 오프라인으로 쌓인 판이 많으면 trace가 수 MB. gzip과 판 단위 분할 전송(2.10) |
| 프레임 변동 | 모바일은 발열과 절전으로 프레임이 흔들리고, 앱 복귀 직후 큰 delta가 한 번 들어올 수 있다. 코드에 `targetFrameRate` 설정이 없어 플랫폼 기본값을 따른다. 시간 경계의 허용 오차는 최악의 delta(0.333초)를 기준으로 잡는다 |
